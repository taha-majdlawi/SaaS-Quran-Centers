## قاعدة البيانات
- **تحقّق محلي من migrations 0001-0020 + فحص شامل لكل سياسات RLS**: ما عندي وصول لمشروع Supabase الفعلي
  تاعك من هالبيئة (لا CLI ولا Docker شغّال ولا بيانات اتصال) - ما قدرت أطبّقها على مشروعك مباشرة. بدلها،
  نصّبت Postgres 16 محلي، بنيت stub بسيط لمخطط `auth`/الأدوار اللي Supabase يوفّرها، وشغّلت كل الـ 20
  migration بالترتيب + بيانات تجريبية (أدمن/معلمين/طالب/ولي أمر بحلقة وحدة، وبيانات بمعظم الجداول الـ51 اللي
  عندها RLS). بعد الشات، عملت فحص منهجي لكل سياسة RLS بالمشروع (مو بس الشات):
  1. فحص ثابت (static) - بنيت graph لكل سياسة بتقرأ جدول تاني عبر subquery، ودوّرت على self-reference
     وعلى دورات (cycles) بين الجداول - ما لقيت وحدة بعد إصلاح الشات.
  2. فحص فعلي (empirical) - شغّلت `SELECT count(*)` على كل جدول من الـ51 (255 استعلام: 51 جدول × 5 أدوار
     مختلفة، بالتبديل الفعلي لهوية المستخدم بين الاستعلامات) - **صفر أخطاء**.
  3. راجعت يدويًا كل سياسة INSERT/UPDATE/DELETE فيها subquery لجدول تاني (12 سياسة) للتأكد من التأشير
     الصحيح للعمود الخارجي.

  هاد كشف وصحّح **4 bugs حقيقية**، كلها بنفس النمط بالضبط (عمود بدون تأشير `alias.` داخل subquery انحل
  للعمود الداخلي بدل الخارجي، فصار الشرط صحيح دايمًا):
  - `chat_participants_select_own_thread` (موجودة أصلًا بـ 0005): أي مشارك بمحادثة وحدة كان يقرأ كل
    المشاركين بكل المحادثات بكل المراكز.
  - `chat_messages_select_participant` **و** `chat_messages_insert_participant` (موجودتين أصلًا بـ 0005،
    اكتُشفتا بس هلأ): نفس المشكلة بالضبط - أي مشارك بمحادثة وحدة كان يقدر **يقرأ محتوى كل الرسائل** بكل
    المحادثات (أخطر من تسريب قائمة الأسماء)، وكمان **يبعت رسالة لمحادثة مو مشارك فيها إطلاقًا**.
  - `chat_threads_delete_own_empty` (من شغلي أنا بـ 0020 - نفس الغلطة بالضبط وأنا بكتبها): كانت بتسمح
    بحذف thread فيه رسائل فعلية تقريبًا دايمًا، رغم إن التعليق بيوعد إنها ما رح تحذف محادثة فيها محتوى.

  كل الأربعة انصلحوا بـ 0020 (بدالة `SECURITY DEFINER` جديدة `chat_thread_participant_ids`، أو بتأشير
  صريح للعمود الخارجي)، وأعدت التحقق الكامل بعدها: أنشأت محادثة "سرّية" بين طرفين ما إلهم علاقة بطالب
  تجريبي، وتأكدت إنه ما يقدر يشوف رسالتها ولا يبعت فيها - نجح الاختبار. كل الـ 20 migration بيتطبّقوا نظيف
  على المحاكاة، وكل الفحوصات الفعلية صفر أخطاء الآن. **لسا لازم إنت تشغّل `supabase db push` (أو تطبّق SQL
  يدويًا) على مشروعك الفعلي** - هاد التحقّق بيثبت صحة الـ SQL منطقيًا، مش إنه انطبق على بيئتك.
