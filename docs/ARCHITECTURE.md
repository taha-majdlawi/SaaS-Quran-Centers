# هيكلية منصة SaaS لمراكز تحفيظ القرآن

هذا المستند يشرح القرارات المعمارية الأساسية لتحويل منتج "اقرأ" (تطبيق موبايل Flutter + لوحة إدارة ويب، كلاهما single-tenant حاليًا) إلى منصة SaaS واحدة تخدم عدة مراكز (tenants) من نفس الكود وقاعدة البيانات.

## 1. نموذج تعدد المستأجرين (Multi-Tenancy)

**القرار: قاعدة بيانات واحدة مشتركة + عزل على مستوى الصف (Row-Level Security) عبر عمود `organization_id`.**

البدائل المرفوضة ولماذا:
- **مشروع Supabase منفصل لكل مركز** (الوضع الحالي): هذا ما يمنع كونه SaaS فعليًا — كل عميل جديد يحتاج نشر تطبيق جديد بالكامل، لا تحديثات مركزية، لا خطط اشتراك، تكلفة تشغيل تتضاعف مع كل عميل.
- **Schema منفصل لكل مستأجر** (نفس المشروع، schema مختلف): يحل مشكلة العزل لكن الترحيلات (migrations) تتضاعف مع عدد المراكز، ولا يدعمها Supabase بشكل طبيعي مع RLS/Realtime.
- **قاعدة بيانات منفصلة فعليًا لكل مستأجر مع بنية تحتية موحّدة**: أفضل عزل لكنه تعقيد تشغيلي غير مبرر في هذه المرحلة (لا يوجد متطلب امتثال/سيادة بيانات يفرضه).

كل جدول بيانات تشغيلي (طلاب، حلقات، حضور، إلخ) يحمل `organization_id` ويُفرض عزله عبر RLS policies تستخدم دوال مساعدة (`public.is_org_member`, `public.is_org_admin`, `public.is_org_staff`) معرّفة في [`supabase/migrations/0001_core_tenancy.sql`](../supabase/migrations/0001_core_tenancy.sql). التفاصيل الكاملة لكل جدول في [`DATA_MODEL.md`](./DATA_MODEL.md).

## 2. الهوية والأدوار

- **هوية مستخدم واحدة عالمية** (`auth.users` + `public.profiles`) يمكنها الانتماء لأكثر من مركز عبر `organization_members`.
- **الدور يُخزَّن لكل عضوية (per-membership) وليس على المستخدم عالميًا** — هذا يختلف عن النظام القديم الذي كان يخزن `role` مباشرة على `profiles` لأنه كان single-tenant. معلّم في مركزَين قد يكون له دور مختلف بكل مركز.
- الأدوار: `student`, `teacher`, `admin`, `guardian` (الأخير جديد — كان موجودًا ضمنيًا فقط في مشروع الويب كصفحات "موافقة ولي أمر").
- **مالك المنصة (Platform Owner)**: دور خارج نطاق أي مستأجر، يُدار عبر `platform_owners`، يقابل لوحة "dev/" القديمة، ويُستخدم لإدارة كل المراكز، الخطط، والفوترة.

## 3. تطبيق الموبايل (Flutter) — `apps/mobile`

يعيد استخدام نفس الأنماط الناجحة من `eqraa_app` (feature-first, Provider, go_router, Supabase, offline sync عبر sqflite) مع إضافة طبقة **سياق المستأجر (Tenant Context)**:

- عند تسجيل الدخول/التسجيل، يختار المستخدم مركزًا (أو ينضم عبر رابط دعوة) — لا يوجد بعد الآن بناء منفصل لكل مركز.
- `lib/core/tenant/` يحمّل بيانات المركز (الاسم، الشعار، الألوان) ديناميكيًا من جدول `organizations` بدل أصول البناء الثابتة (build-time assets) المستخدمة سابقًا للعلامة التجارية الخاصة بكل عميل.
- كل استعلام Supabase يُمرّر `organization_id` الحالي ضمنيًا عبر RLS (لا حاجة لفلترة يدوية بفضل `auth.uid()` + `organization_members`).
- طبقة المزامنة دون اتصال (`core/offline`) تبقى كما هي بنيويًا؛ فقط تضيف `organization_id` لصفوف قائمة الانتظار (outbox).

## 4. تطبيق الويب (Next.js) — `apps/web`

ترقية من HTML/CSS/JS ثابت إلى **تطبيق Next.js واحد** يخدم ثلاث مناطق عبر `middleware.ts` بناءً على الـ hostname:

| النطاق | المسار الداخلي | الوظيفة | يقابل (القديم) |
|---|---|---|---|
| `quran-centers.app` (الجذر) | `app/(marketing)` | موقع تسويقي للمنصة نفسها + تسجيل مراكز جديدة | `index.html` |
| `admin.quran-centers.app` | `app/(platform)` | لوحة مالك المنصة: كل المراكز، الخطط، الفوترة، أعلام الميزات | `dev/` |
| `{slug}.quran-centers.app` | `app/(tenant)/[org]` | لوحة إدارة المركز — 22 موديول (طلاب، معلمين، حلقات، سرد، نقاط...) | `admin/*` |

كل موديولات `admin/` القديمة (17+ موديول) تتحول لمسارات فرعية تحت `app/(tenant)/[org]/`، تشترك في مكوّن تخطيط (layout) واحد بدل تكرار HTML/CSS في كل صفحة — وهذا يحل المشكلة التي دفعت لاختيار Next.js أصلًا (22 صفحة ثابتة متشابهة بدون أي مكوّنات مشتركة).

## 5. تدفق الطلب النموذجي (مثال: معلم يسجّل حضور من لوحة الويب)

1. المتصفح يطلب `alnoor.quran-centers.app/attendance`.
2. `middleware.ts` يقرأ الـ hostname، يستخرج `slug=alnoor`، يعيد الكتابة داخليًا إلى `/app/(tenant)/[org]/attendance` مع `org=alnoor`.
3. الصفحة تجلب `organization_id` عبر استعلام `organizations` بالـ `slug` (مع تخزين مؤقت خفيف)، ثم تستدعي Supabase مباشرة من المتصفح (نفس نمط النظام القديم — anon key + RLS)، لكن الآن RLS تتحقق من `organization_members` بدل الثقة بمشروع Supabase بالكامل.
4. سياسات RLS في `0003_attendance_recitation.sql` تسمح بالكتابة فقط إذا `public.is_org_staff(organization_id)` صحيحة لهذا المستخدم **ولهذا المركز تحديدًا**.

## 6. الفوترة والخطط

هيكل أولي فقط (`plans`, `subscriptions` في `0001_core_tenancy.sql`) — بدون تكامل فعلي مع مزوّد دفع بعد. الحقل `billing_provider` جاهز لإضافة Stripe لاحقًا دون تغيير الشكل العام للجدول.

## 7. ما لم يُبنَ بعد (متعمّدًا خارج نطاق السكيلتون)

- منطق العمل الفعلي لكل موديول (شاشات، نماذج، تقارير) — البنية جاهزة لاستيعابه فقط.
- تكامل فوترة حقيقي (Stripe webhooks).
- Custom Access Token Hook لوضع `organization_id` النشط داخل الـ JWT (تحسين أداء مستقبلي بدل الاعتماد الكامل على استعلام `organization_members` بكل RLS check).
- اختبارات آلية (unit/integration) لسياسات RLS.
